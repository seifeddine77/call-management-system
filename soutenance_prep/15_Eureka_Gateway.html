Infrastructure : Eureka & API Gateway

Analyse détaillée du routage, de l'authentification et de la sécurité réseau

1. Eureka Server (Service Registry)

Le serveur Eureka sert d'annuaire de services pour l'architecture microservices. Chaque instance de microservice (Auth, Tickets, etc.) s'enregistre auprès de lui au démarrage, évitant ainsi d'écrire des adresses IP fixes dans les configurations.

🔍 Note d'implémentation
Pour notre environnement de démonstration, nous désactivons le mode Self-Preservation : eureka.server.enableSelfPreservation = false. Cela permet de retirer instantanément de l'annuaire une instance éteinte brusquement en local.
server: port: 8761 spring: application: name: eureka-server eureka: client: registerWithEureka: false # Ne s'enregistre pas lui-même fetchRegistry: false server: enableSelfPreservation: false # Nettoyage immédiat en dev

2. API Gateway (Spring Cloud Gateway)

L'API Gateway écoute sur le port 8080. Elle constitue l'unique point de passage public du frontend et du mobile, s'occupant d'équilibrer la charge de manière réactive.

🔗 Routage Dynamique Eureka
Les destinations des routes utilisent le protocole d'équilibrage de charge lb:// (ex: lb://ticket-service) pour contacter dynamiquement les conteneurs enregistrés.
🔐 Sécurisation Centralisée
Le routage applique les filtres JwtAuthFilter et RoleFilter pour rejeter ou valider les utilisateurs en amont des microservices.

3. Le Filtre d'Authentification (JwtAuthFilter)

Fichier : JwtAuthFilter.java. Ce filtre intercepte les requêtes sécurisées pour vérifier le token JWT et propager les informations de session.

⚠️ Gestion des requêtes OPTIONS (CORS)
Le filtre laisse systématiquement passer les requêtes HTTP de méthode OPTIONS (Preflight). Ces requêtes, envoyées par les navigateurs avant un appel API pour vérifier les droits CORS, ne contiennent jamais d'en-tête de sécurité. Les rejeter bloquerait toute l'application web.
// Bypass CORS preflight if (request.getMethod() == HttpMethod.OPTIONS) { return chain.filter(exchange); } // Vérifier et extraire le token JWT... String token = authHeader.substring(7); SecretKey key = Keys.hmacShaKeyFor(jwtSecret.getBytes()); Claims claims = Jwts.parser().verifyWith(key).build().parseSignedClaims(token).getPayload(); // Header Injection (Downstream forwarding) ServerHttpRequest modifiedRequest = request.mutate() .header("X-User-Id", claims.getSubject()) .header("X-User-Role", claims.get("role", String.class)) .header("X-User-Agence-Id", claims.get("agenceId", String.class)) .build();

Concept clé de l'injection d'en-têtes (Header Injection) : Le microservice backend en aval n'a pas besoin de décoder le JWT ni d'accéder à la clé de sécurité. Il lui suffit de lire X-User-Role ou X-User-Id dans les en-têtes HTTP de la requête, ce qui le rend totalement autonome et léger.

4. Filtre de Contrôle des Rôles (RoleFilter)

Fichier : RoleFilter.java. Ce filtre limite l'accès aux endpoints d'administration ou de paramétrage (comme l'édition des règles métiers ou la gestion des agences).

  • Il récupère la valeur X-User-Role injectée lors de l'étape précédente.
  • Il vérifie la présence de ce rôle dans la liste configurée de la route (ex: SUPERVISOR,ADMIN).
  • En cas d'absence ou d'incompatibilité, la Gateway rejette directement la requête avec un code 403 Forbidden au format JSON, sans solliciter le microservice cible.

5. Rate Limiting Réparti par Client IP

La Gateway implémente un filtre de limitation de flux (Rate Limiter) basé sur Redis à l'aide de l'algorithme Token Bucket :

// Configuration du KeyResolver - RateLimiterConfig.java public KeyResolver ipKeyResolver() { return exchange -> { String ip = exchange.getRequest().getHeaders().getFirst("X-Forwarded-For"); if (ip == null || ip.isBlank()) { ip = exchange.getRequest().getRemoteAddress().getAddress().getHostAddress(); } else { ip = ip.split(",")[0].trim(); // Prendre la première adresse de passage } return Mono.just(ip); }; }

Importance de X-Forwarded-For : Si nous utilisions uniquement l'adresse IP distante physique brute (Remote Address), la Gateway limiterait l'adresse IP globale de notre proxy Nginx Ingress Kubernetes, bloquant ainsi tous les utilisateurs en même temps. En lisant X-Forwarded-For, nous ciblons la véritable IP de chaque utilisateur final.

6. Préparation de la Soutenance (Questions/Réponses)

Question Classique Argument de Défense Technique
Quel est le rôle du filtre OPTIONS dans JwtAuthFilter ? OPTIONS est la requête de pré-vérification CORS envoyée par le navigateur. Elle ne contient aucun en-tête d'authentification. Si nous ne la laissions pas passer, toutes les requêtes web échoueraient avec une erreur d'accès.
Comment se transmettent les rôles utilisateurs aux microservices ? La Gateway valide la signature du token JWT une seule fois, puis injecte les informations extraites dans des en-têtes HTTP personnalisés (comme X-User-Role). Les microservices en aval n'ont qu'à lire ces en-têtes, ce qui les maintient découplés, légers et stateless.
Pourquoi utiliser Redis pour le Rate Limiting ? Parce que la Gateway peut être scalée sur plusieurs conteneurs. Avoir un compteur en mémoire locale dans chaque Gateway ne fonctionnerait pas. Redis offre un stockage distribué partagé ultra-rapide en mémoire pour décompter les jetons de requête.
