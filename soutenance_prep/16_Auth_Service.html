Microservice d'Authentification (Auth-Service)

Analyse détaillée du traitement de connexion, du chiffrement et de l'architecture de repli

1. Rôle et Architecture

Le microservice auth-service écoute sur le port 8081. Il est chargé de valider l'identité des utilisateurs, de chiffrer les mots de passe et de délivrer les autorisations d'accès.

Spring Boot 3 Spring Cloud OpenFeign JJWT (JSON Web Token) BCrypt Password Encoder PostgreSQL

Pour respecter le principe d'isolation des données (Database-per-Service), les profils des collaborateurs sont hébergés dans organisation-service. L'authentification délègue la recherche et la création via des appels réseaux synchrones.

2. Stratégie de double jeton et Rotation

Lors de la connexion, deux jetons sont créés : un Access Token (durée de vie courte, contient le rôle et l'agence pour la Gateway) et un Refresh Token (durée de vie longue, stocké en base de données).

🔒 Rotation de Refresh Token (Sécurité de pointe)
Chaque fois qu'un utilisateur demande à rafraîchir sa session, le microservice vérifie le jeton, le révoque immédiatement en base de données (revoked = true) et renvoie un tout nouveau couple de jetons. Cela empêche le rejeu d'un jeton dérobé.
// Extrait de AuthServiceImpl.java RefreshToken storedToken = refreshTokenRepository.findByToken(refreshTokenStr) .orElseThrow(() -> new UnauthorizedException("Refresh token non trouvé")); if (storedToken.isRevoked()) { throw new UnauthorizedException("Refresh token déjà révoqué"); } // Révocation systématique (Rotation) storedToken.setRevoked(true); refreshTokenRepository.save(storedToken); // Génération du nouveau couple de tokens return generateTokens(user);

3. Communication synchrone (Spring Cloud OpenFeign)

Pour communiquer de manière propre et déclarative avec le service d'organisation sans écrire de code de bas niveau HTTP (comme RestTemplate), nous déclarons une interface Feign :

@FeignClient( name = "organisation-service", url = "${USER_SERVICE_URL:}", fallbackFactory = UserServiceClientFallbackFactory.class ) public interface UserServiceClient { @GetMapping("/api/users/email/{email}") ResponseEntity<UserDto> findByEmail(@PathVariable("email") String email); }

Spring Cloud résout le nom organisation-service en interrogeant Eureka et effectue la requête HTTP de façon transparente.

4. Résilience & Base de données Cache Locale

Si le service d'organisation tombe en panne, le disjoncteur Feign coupe le circuit et fait appel à UserServiceClientFallbackFactory.

🛡️ Résilience d'accès
Au lieu de retourner une erreur 500, la fabrique de repli interroge une table locale local_users gérée dans la base auth_db. Si l'utilisateur s'est déjà connecté une fois, son compte y est mis en cache, lui permettant d'ouvrir sa session même en mode dégradé (sans réseau interne).
// Extrait de UserServiceClientFallbackFactory.java public UserServiceClient create(Throwable cause) { log.warn("organisation-service indisponible, bascule sur la DB locale"); return new UserServiceClient() { @Override public ResponseEntity<UserDto> findByEmail(String email) { Optional<LocalUser> local = localUserRepository.findByEmail(email); if (local.isEmpty()) return ResponseEntity.notFound().build(); LocalUser u = local.get(); return ResponseEntity.ok(UserDto.builder() .id(u.getId()).email(u.getEmail()) .passwordHash(u.getPasswordHash()).role(u.getRole()).actif(u.isActif()) .build()); } }; }

5. Soutenance d'Auth-Service (Questions/Réponses)

Question du jury Défense Technique
Pourquoi diviser Auth et Organisation dans deux services ? Pour l'isolation. Le service d'authentification est un module technique critique à forte charge. Les profils utilisateurs (organisation) changent selon les agences. Cette séparation évite qu'un bug sur le paramétrage d'une agence n'empêche l'ensemble du système de se connecter.
Comment sécurisez-vous les mots de passe ? Nous utilisons BCrypt (via le PasswordEncoder de Spring Security). C'est un algorithme de hachage robuste intégrant un sel unique et un facteur de coût ajustable pour empêcher les attaques par table de hachage (rainbow tables) ou par force brute.
Comment fonctionne votre mécanisme de repli (Fallback) ? Si organisation-service ne répond plus, nous interceptons l'erreur grâce à la FallbackFactory d'OpenFeign. Nous basculons sur une copie locale des comptes enregistrés dans la table local_users, garantissant la résilience du système.
