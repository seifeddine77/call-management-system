Microservice d'Organisation (Organisation-Service)

Référentiel centralisé des agences physiques et des comptes collaborateurs

1. Rôle et Architecture

Le microservice organisation-service écoute sur le port 8082. Il constitue le référentiel d'autorité des agences physiques et des comptes collaborateurs.

Spring Boot 3 Spring Data JPA (Hibernate) PostgreSQL Flyway Migrations RabbitMQ

Il expose des endpoints administratifs et opérationnels pour la gestion des collaborateurs (Opérateurs, Superviseurs, Administrateurs) et des informations d'agences (stock de pièces de rechange, localisation, coordonnées).

2. Règles Métiers & Validation (CDC 1.A et 1.B)

Le service d'organisation garantit la cohérence des structures en vérifiant rigoureusement les contraintes spécifiées par le cahier des charges :

🏢 CDC 1.A : Rattachement Obligatoire
Dans UserServiceImpl.java, tout collaborateur ayant le rôle OPERATOR ou SUPERVISOR doit obligatoirement être rattaché à une agence physique lors de sa création ou mise à jour.
👑 CDC 1.B : Responsabilité d'Agence
Dans AgenceServiceImpl.java, le responsable désigné pour gérer une agence physique doit impérativement être un utilisateur ayant le rôle SUPERVISOR.
// Validation du rattachement obligatoire dans UserServiceImpl if (("OPERATOR".equals(role) || "SUPERVISOR".equals(role)) && agenceId == null) { throw new IllegalArgumentException("Un opérateur/superviseur doit être rattaché à une agence"); } // Validation du responsable d'agence dans AgenceServiceImpl if (!"SUPERVISOR".equals(user.getRole())) { throw new IllegalArgumentException("Le responsable d'une agence doit être un SUPERVISOR"); }

3. Relations JPA et Piège Lombok (Hibernate)

Pour lier l'entité User à son Agence correspondante, nous utilisons JPA avec une attention particulière aux performances et à la stabilité :

⚡ FetchType.LAZY (Lazy Loading)
La liaison est annotée avec @ManyToOne(fetch = FetchType.LAZY). Cela évite le chargement automatique et systématique de l'objet Agence complet à chaque fois qu'un utilisateur est récupéré en base, éliminant les requêtes N+1 et le surcoût réseau.
⚠️ Risque de StackOverflowError
Dans une relation bidirectionnelle (User rattaché à Agence, et Agence contenant une liste de Users), laisser Lombok générer automatiquement les méthodes toString(), equals() et hashCode() provoque des appels récursifs infinis.

Solution : L'ajout explicite des annotations @ToString.Exclude et @EqualsAndHashCode.Exclude sur les propriétés relationnelles coupe cette récursion.
// Extrait de User.java @Entity @Table(name = "users") @Getter @Setter public class User { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id; private String email; @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "agence_id") @ToString.Exclude @EqualsAndHashCode.Exclude private Agence agence; }

4. Découplage Événementiel via RabbitMQ

Les modifications de structure (nouveau compte, nouvelle agence) doivent être notifiées aux autres services sans introduire de couplage fort ou ralentir l'expérience utilisateur.

Le service publie des événements asynchrones sur le Topic Exchange user.exchange :

  • user.created : Reçu par notification-service pour envoyer le mail Thymeleaf d'accueil.
  • agence.created : Reçu par whatsapp-service pour créer la discussion de groupe d'agence.
🛡️ Résilience du Publisher
La publication RabbitMQ est encapsulée dans un bloc de capture d'exceptions. Si le broker de messages RabbitMQ subit une indisponibilité, l'écriture en base de données de l'utilisateur n'est pas bloquée, garantissant la continuité opérationnelle.
// Extrait de UserEventPublisher.java try { eventPublisher.publishUserCreated(event); } catch (Exception e) { log.warn("Failed to publish UserCreatedEvent (RabbitMQ down): {}", e.getMessage()); }

5. Questions / Réponses types pour le Jury

Question du jury Défense Technique
Pourquoi utiliser FetchType.LAZY pour la relation Agence dans l'entité User ? Par défaut, les relations @ManyToOne dans JPA sont configurées en FetchType.EAGER (chargement immédiat). Cela signifie que charger 100 utilisateurs effectuerait 100 requêtes supplémentaires pour récupérer les détails des agences, même si nous n'en avons pas besoin. FetchType.LAZY diffère la requête jusqu'à l'appel explicite de user.getAgence(), ce qui optimise grandement les performances de la base de données.
Pourquoi désactiver les exclusions Lombok sur les liaisons bidirectionnelles ? Si nous laissons Lombok générer automatiquement la méthode toString() sur User et Agence sans les exclure, appeler user.toString() va évaluer la propriété agence, qui à son tour va évaluer la liste de ses utilisateurs, créant une boucle infinie se terminant par un plantage StackOverflowError de la JVM.
Pourquoi ne pas bloquer la création de compte si le message RabbitMQ échoue ? C'est le principe du découplage lâche. La création d'un collaborateur est une opération transactionnelle critique qui doit aboutir. L'envoi du mail de bienvenue ou l'ouverture du salon WhatsApp sont des effets de bord asynchrones. Si RabbitMQ subit une micro-coupure, nous loggons l'avertissement mais laissons la création de l'utilisateur s'effectuer pour ne pas perturber l'administration.
